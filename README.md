# Граф зависимостей пакетов: вариант 17

Практическая работа № 2 по дисциплине «Конфигурационное управление».
**Этап 4: дополнительные операции. Вариант 17 — .NET (NuGet).**

Приложение строит граф прямых и транзитивных зависимостей указанной версии
NuGet-пакета. Обход выполняется алгоритмом DFS без рекурсии, через явный стек.
Поддерживаются исключение пакетов по подстроке, циклы и тестовый репозиторий
в локальном текстовом файле с именами пакетов из больших латинских букв.
Флаг `--load-order` выводит порядок загрузки: каждый пакет следует после
своих зависимостей, исходный пакет завершается последним. Если в достижимом
графе есть цикл, программа сообщает, почему такой порядок невозможен.
Используется только стандартная библиотека Python; менеджеры пакетов
и сторонние библиотеки для получения зависимостей не используются.

Этапы сохранены в ветках `stage1`, `stage2`, `stage3`, `stage4`. Эта ветка
добавляет только четвёртый этап к результату третьего. PlantUML
и создание SVG относятся к этапу 5 и здесь не реализованы.

## Требования и запуск

Нужен Python 3.10 или новее. Все команды выполняются из корня проекта.
Для реального репозитория нужен доступ к HTTP(S) NuGet V3; тестовый режим
работает без сети.

```sh
python3 src/main.py --help
python3 src/main.py \
  --package Newtonsoft.Json \
  --repository https://api.nuget.org/v3/index.json \
  --version 13.0.3 \
  --output graph.svg
```

Запуск через Makefile:

```sh
make run ARGS="--package A --repository examples/repository.txt \
--version 1.0.0 --output graph.svg --test-mode"
```

## Все настройки

| Опция | Обязательность | Назначение |
| --- | --- | --- |
| `--package` | Обязательна | Имя исходного пакета. |
| `--repository` | Обязательна | URL индекса NuGet V3 или путь к тестовому файлу. |
| `--version` | Обязательна | Конкретная версия исходного NuGet-пакета. |
| `--output` | Обязательна | Путь будущего SVG, проверяется без записи. |
| `--filter` | По умолчанию `""` | Подстрока в именах исключаемых пакетов. |
| `--test-mode` | Флаг, по умолчанию выключен | Читать локальный тестовый файл. |
| `--load-order` | Флаг, по умолчанию выключен | Вывести порядок загрузки вместо списка смежности. |

В тестовом формате версии отсутствуют: `--version` проверяется как на этапе 1,
но при построении тестового графа не используется. Относительные пути
отсчитываются от текущего рабочего каталога; поддерживается `~`.
Значения с пробелами заключают в кавычки. Флаги `--test-mode` и `--load-order`
не принимают значений `true` или `false`.

Проверяются имя пакета, числовая версия с необязательным суффиксом,
HTTP(S) URL репозитория, путь с расширением `.svg` и значение фильтра.
Неизвестные и сокращённые опции, управляющие символы и фильтр только
из пробелов отвергаются. Путь вывода проверяется без создания или изменения
файла. Существующий файл изображения сохраняет своё содержимое.

## Построение графа и фильтрация

Вершина NuGet-графа — пара «имя, конкретная версия». Имена NuGet-пакетов
сравниваются без учёта регистра, для вывода сохраняется первое написание.
Разные версии одного пакета образуют разные вершины. В тестовом графе
вершина определяется только именем.

Алгоритм использует стек пар «вершина, итератор исходящих зависимостей»:

1. Добавить исходную вершину в граф и её итератор в стек.
2. Получить следующее ребро вершины на вершине стека.
3. Если имя зависимости содержит непустой фильтр, пропустить её.
4. Добавить ребро в граф. Если целевая вершина ещё не посещена, добавить
   её в граф и поместить её итератор в стек, сразу углубившись в эту ветвь.
5. Если итератор исчерпан, удалить его из стека. Продолжать до пустого стека.

Вершина отмечается посещённой до обхода её потомков. Поэтому цикл
и самопетля сохраняются как рёбра, но повторный обход уже посещённой
вершины не выполняется. Рёбра к общим зависимостям не теряются,
повторяющиеся одинаковые рёбра объединяются. Несвязанные с исходным
пакетом компоненты не обходятся. Рекурсия не используется.

Фильтр — обычная подстрока **с учётом регистра**, без шаблонов и регулярных
выражений; пустая строка ничего не исключает. Он проверяется по имени
из зависимости до выбора версии и сетевых запросов к этому пакету.
Исключённая ветвь не обходится. Если её потомок достижим другим путём,
он остаётся в графе. Исключение исходного пакета даёт пустой граф;
в режиме NuGet в этом случае запросов к репозиторию нет.

## Получение данных NuGet

1. Прочитать JSON-индекс `--repository` и найти `PackageBaseAddress/3.0.0`.
2. Нормализовать указанную пользователем версию исходного пакета.
3. Загрузить `{base}/{package}/{version}/{package}.nuspec`.
4. Прочитать XML-зависимости из `metadata/dependencies/dependency`
   и `metadata/dependencies/group/dependency` для всех групп платформ.
5. Для разрешённой зависимости получить `{base}/{package}/index.json`
   и выбрать минимальную доступную версию, удовлетворяющую ограничению.
6. Продолжить DFS по манифесту выбранной версии.

Версия исходного пакета берётся точно из `--version`. В версиях удаляются
начальные нули и метаданные после `+`, недостающие числовые компоненты
дополняются до трёх; четвёртый нулевой компонент удаляется. Суффикс
предварительной версии переводится в нижний регистр.
Например, `01.2.003.0+build` → `1.2.3`.

Поддержаны ограничения `.nuspec`: `1.0` (минимум включительно),
`[1.0]` (точная версия), `[1.0,2.0)`, `(1.0,2.0]`, `[1.0,)`, `(,2.0)`
и другие сочетания открытых и закрытых границ. Без ограничения выбирается
минимальная стабильная версия. Предварительные версии допускаются,
если хотя бы одна граница ограничения явно содержит prerelease-суффикс.
Числовые компоненты и числовые части prerelease сравниваются как числа.
Ошибочный диапазон и отсутствие подходящей версии дают понятную ошибку.

Индекс сервиса читается один раз, список версий — один раз для каждого
имени, каждый манифест — один раз для пары «имя, версия».
Результат выбора по одинаковому имени и ограничению также кешируется.
Группы платформ объединяются, поскольку выбор платформы не задан.
Ограничения разрешаются отдельно для каждого ребра; граф показывает
все полученные версии, без глобального согласования версий для установки.

Использованы официальные описания
[NuGet Package Content API](https://learn.microsoft.com/en-us/nuget/api/package-base-address-resource),
[версий и диапазонов](https://learn.microsoft.com/en-us/nuget/concepts/package-versioning)
и [формата .nuspec](https://learn.microsoft.com/en-us/nuget/reference/nuspec).

Разбор XML поддерживает пространство имён как на `package`, так и только
на `metadata`, что встречается в старых транзитивных пакетах.

Пример реального графа:

```sh
python3 src/main.py --package jQuery.Validation --version 1.21.0 \
  --repository https://api.nuget.org/v3/index.json --output graph.svg
```

```text
jQuery.Validation@1.21.0: jQuery@1.4.4
jQuery@1.4.4:
```

## Тестовый репозиторий и формат вывода

Файл UTF-8 (также допускается UTF-8 с BOM) содержит списки смежности:

```text
A: B C
B: C
C:
```

Каждый пакет, включая листовой, должен быть явно описан ровно один раз.
Имена состоят из одной или нескольких букв `A-Z`. Порядок объявления
пакетов произвольный; пробелы вокруг `:` и пустые строки допускаются.
Повторяющиеся зависимости в строке объединяются с сохранением порядка.
Комментарии, запятые, версии, цифры и строчные буквы не поддерживаются.
Весь файл проверяется на корректность, включая недостижимые компоненты.
Неописанная зависимость, повторное объявление и неверный формат — ошибки.
Пустой файл или отсутствие исходного пакета также дают ошибку.

CLI выводит список смежности: `пакет: зависимости`. Для NuGet используется
метка `имя@версия`, например `A@1.0.0: B@2.0.0`. Листовая вершина выводится
как `C:`. Строки идут в порядке открытия вершин DFS, рёбра — в порядке
манифеста или тестового файла. Это представление графа, а не порядок загрузки.
Вывод начинается только после успешного построения всего графа.

### Транзитивная зависимость

```sh
python3 src/main.py --package A --version 1.0.0 \
  --repository examples/repository.txt --test-mode --output graph.svg
```

```text
A: B C
B: C
C:
```

### Общая зависимость и несвязная компонента

```sh
python3 src/main.py --package A --version 1.0.0 \
  --repository examples/diamond.txt --test-mode --output graph.svg
```

```text
A: B C
B: D
D:
C: D
```

Вершина `D` посещается до `C`, ребро `C → D` сохраняется.
Компонента `X → Y` не входит в результат.

### Исключение пакета и его ветви

```sh
python3 src/main.py --package A --version 1.0.0 --filter B \
  --repository examples/diamond.txt --test-mode --output graph.svg
```

```text
A: C
C: D
D:
```

`B` исключён; `D` остаётся достижимым через `C`.
С фильтром `A` выводится `Граф пуст: исходный пакет исключён фильтром.`

### Цикл

```sh
python3 src/main.py --package A --version 1.0.0 \
  --repository examples/cycle.txt --test-mode --output graph.svg
```

```text
A: B
B: C
C: A
```

### Самопетля и листовой пакет

```sh
python3 src/main.py --package A --version 1.0.0 \
  --repository examples/self_loop.txt --test-mode --output graph.svg
python3 src/main.py --package C --version 1.0.0 \
  --repository examples/repository.txt --test-mode --output graph.svg
```

Первый запуск выводит `A: A`, второй — `C:`.

## Порядок загрузки зависимостей: этап 4

Режим включается флагом `--load-order`. Без него по-прежнему выводится
список смежности. Все остальные параметры, включая обязательный `--output`,
сохраняются. Изображение не создаётся и существующий SVG не изменяется.

Порядок загрузки понимается как последовательность подготовки пакетов,
в которой все зависимости пакета уже подготовлены к моменту самого пакета.
Это топологический порядок с зависимостями перед потребителем. Каждая
вершина выводится один раз, по одной на строку; исходный пакет включён
и стоит последним. Для NuGet сохраняется формат `имя@версия`.

После построения графа применяется DFS без рекурсии с явным стеком:

1. Поместить вершину и итератор её зависимостей в стек активного пути.
2. Перейти к ещё не завершённой зависимости в порядке объявления рёбер.
3. Когда все зависимости вершины завершены, добавить её в результат.
4. Ребро к вершине активного пути означает цикл: вернуть ошибку с его путём.

Для независимых ветвей допустимо несколько порядков. Выбран воспроизводимый
порядок завершения DFS по порядку рёбер исходного графа. Общая зависимость
выводится до всех её потребителей. Операция занимает `O(V + E)` времени
и `O(V)` дополнительной памяти, где `V` и `E` — вершины и рёбра построенного
графа. Сам граф строится неизменённым алгоритмом этапа 3.

Фильтрация выполняется до вычисления порядка: исключённые пакеты и ветви
не участвуют. Недостижимые компоненты, включая циклические, не участвуют.
Цикл или самопетля в достижимом графе делают порядок невозможным.
В этом случае код завершения `2`, сообщение отправляется в `stderr`,
`stdout` остаётся пустым, даже если часть ветвей уже обработана.
Весь результат вычисляется до начала вывода.

### Транзитивные зависимости

```sh
python3 src/main.py --package A --version 1.0.0 \
  --repository examples/repository.txt --test-mode \
  --output graph.svg --load-order
```

```text
C
B
A
```

В файле `A` зависит от `B` и `C`, а `B` — от `C`. Поэтому `C` идёт первым,
затем `B`, затем `A`.

### Общий потомок, фильтр и несвязная компонента

```sh
python3 src/main.py --package A --version 1.0.0 \
  --repository examples/diamond.txt --test-mode \
  --output graph.svg --load-order
```

```text
D
B
C
A
```

`D` нужен обоим пакетам `B` и `C`, но выводится один раз. Компонента `X → Y`
не входит в результат. При добавлении `--filter B` результат — `D`, `C`, `A`,
каждый на отдельной строке. При `--filter A`:

```text
Порядок загрузки пуст: исходный пакет исключён фильтром.
```

### Листовой пакет, цикл и самопетля

```sh
python3 src/main.py --package C --version 1.0.0 \
  --repository examples/repository.txt --test-mode \
  --output graph.svg --load-order
```

Результат — одна строка `C`. Примеры циклов:

```sh
python3 src/main.py --package A --version 1.0.0 \
  --repository examples/cycle.txt --test-mode \
  --output graph.svg --load-order
python3 src/main.py --package A --version 1.0.0 \
  --repository examples/self_loop.txt --test-mode \
  --output graph.svg --load-order
```

Первый запуск возвращает ошибку:

```text
Ошибка: порядок загрузки невозможен: цикл A -> B -> C -> A
```

Второй возвращает `Ошибка: порядок загрузки невозможен: цикл A -> A`.
Оба завершаются с кодом `2`, без частичного порядка в `stdout`.

## Сравнение с реальным NuGet

Сравнение фактически выполнено 20.10.2026: .NET SDK **8.0.426**,
NuGet **6.11.2.1**, проект `PackageReference` для `net8.0`, источник
`https://api.nuget.org/v3/index.json`, точная версия `jQuery.Validation 1.21.0`.
Кеши SDK и NuGet изолированы во временном каталоге, кеш пакетов изначально
пустой. Менеджер пакетов используется только для проверки результатов,
приложение его не вызывает.

Повторная проверка **27.10.2026** выполнена с теми же версиями SDK и NuGet
в новом временном каталоге. Для каждого примера использован отдельный пустой
кеш пакетов и HTTP. Оба `dotnet restore` завершились с кодом `0`.

| Исходный пакет | Вывод `--load-order` | GET архивов в журнале NuGet |
| --- | --- | --- |
| `jQuery.Validation 1.21.0` | `jQuery 1.4.4` → `jQuery.Validation 1.21.0` | `jQuery.Validation` → `jQuery` |
| `jQuery 1.4.4` | Только `jQuery 1.4.4` | Только `jQuery 1.4.4` |

Для обоих запусков состав пакетов и версии из нашего вывода проверены
по `targets` файла `obj/project.assets.json` реального NuGet. Дополнительно
проверено, что каждая зависимость из этого файла предшествует своему
потребителю в нашем порядке. В первом примере NuGet подтвердил зависимость
`jQuery.Validation 1.21.0` от `jQuery 1.4.4`. Во втором зависимостей нет,
поэтому различий состава и последовательности не обнаружено.

Чтобы повторить второй пример, в копии `Compare.csproj` заменить
`Include="jQuery.Validation" Version="[1.21.0]"` на
`Include="jQuery" Version="[1.4.4]"`, выполнить restore в новом временном
каталоге и запустить нашу программу с `--package jQuery --version 1.4.4`.


Для повторения сравнения нужен установленный .NET SDK 8. Из корня репозитория
скопировать подготовленные исходные настройки во временный каталог:

```sh

export NUGET_PACKAGES="$comparison_dir/packages"

export DOTNET_SKIP_FIRST_TIME_EXPERIENCE=1

dotnet restore "$comparison_dir/Compare.csproj" \
  --configfile "$comparison_dir/NuGet.Config" \
  --no-cache --force --verbosity normal > "$comparison_dir/restore.log" 2>&1
cat "$comparison_dir/restore.log"
```

В `Compare.csproj` указано точное ограничение `[1.21.0]`; аудит уязвимостей
отключён только для этого сравнения, чтобы журнал содержал запросы пакетов.
`NuGet.Config` оставляет единственный источник nuget.org. Сам SDK был временно
распакован в `/tmp` официальным `dotnet-install.sh --channel 8.0 --no-path`;
системная установка не менялась. Пакеты и артефакты NuGet в Git не добавляются.

В `obj/project.assets.json` получены вершины `jQuery/1.4.4`
и `jQuery.Validation/1.21.0`; вторая содержит зависимость `jQuery: 1.4.4`.
Это подтверждает совпадение состава, версий и направления зависимости.
Порядок ключей JSON не считается порядком загрузки.

Расхождение в последовательности объясняется назначением операций:
программа строит порядок готовности зависимостей, NuGet выполняет restore —
скачивание и распаковку архивов. В этом запуске NuGet сначала получил архив
исходного пакета, затем архив его зависимости. Скачивание архива возможно
до получения его зависимостей; это не нарушает зависимость в итоговом графе.
Поэтому порядок HTTP-запросов или строк «Установлено» не обязан совпадать
с топологическим порядком. При других запусках на него также могут влиять
кеш и параллельная работа; в программе порядок определяется графом.

Для других пакетов возможны и различия состава: программа этапа 3 объединяет
группы платформ и разрешает каждое ребро отдельно, а NuGet выбирает зависимости
для целевой платформы и согласует одну версию пакета на проект. Пользовательский
фильтр также намеренно исключает часть графа. На выбранном примере без фильтра
эти различия не проявились. Изменять разрешение зависимостей этапа 3 для этого
сравнения не потребовалось.

Официальные описания Microsoft:
[Package Restore](https://learn.microsoft.com/en-us/nuget/consume-packages/package-restore),
[разрешение зависимостей](https://learn.microsoft.com/en-us/nuget/concepts/dependency-resolution).

## Обработка ошибок

Успешный запуск и `--help` возвращают `0`. Ошибки аргументов, получения
данных и цикла при `--load-order` возвращают `2`; сообщение идёт в `stderr`,
`stdout` остаётся пустым.
Обрабатываются ошибки чтения и кодировки файла, формата тестового графа,
отсутствие пакета/версии, HTTP-ошибки, недоступность сети, тайм-аут,
неверный JSON, отсутствие `PackageBaseAddress`, неверный адрес ресурса,
неверный XML, повреждённые списки версий и неподходящие диапазоны.
Тайм-аут каждой сетевой операции — 20 секунд.

Если Python сообщает `CERTIFICATE_VERIFY_FAILED`, нужно настроить доверенные
корневые сертификаты в используемом Python или переменную `SSL_CERT_FILE`.
Приложение использует стандартную проверку TLS-сертификата.
На macOS можно явно указать системное хранилище сертификатов:

```sh
SSL_CERT_FILE=/etc/ssl/cert.pem python3 src/main.py \
  --package Newtonsoft.Json --version 13.0.3 \
  --repository https://api.nuget.org/v3/index.json --output graph.svg
```

## Сборка и тесты

```sh
make build
make test
```

Без `make`:

```sh
python3 -m compileall -q src
python3 -m unittest discover -s tests -v
```

Отдельная сборка для запуска не требуется. Создаваемый `__pycache__`
исключён из Git. Тесты не обращаются к внешним репозиториям: для проверки
реального CLI используется HTTP-сервер на `127.0.0.1` со случайным портом.
Окружение должно разрешать локальные сокеты.

Проверяются все параметры, NuGet XML и JSON, диапазоны версий, запрос
конкретной версии, DFS на цепочке из 1500 вершин, циклы и самопетли,
общие зависимости, несвязные компоненты, повторяющиеся рёбра,
разные версии одного пакета, кеширование, фильтр до запросов,
ошибки тестового файла и сохранность существующего SVG.
Всего 69 тестов, включая 15 проверок этапа 4: порядок на цепочке,
ромбе и независимых ветвях, инвариант топологического порядка на 30
воспроизводимых графах, цепочка из 1500 вершин, фильтры, циклы с путём
ошибки, отсутствие частичного вывода и работа с NuGet через локальный HTTP.
