# Граф зависимостей пакетов: вариант 17

Практическая работа № 2, **этап 4: дополнительные операции**, ветка `stage4`.
Приложение строит граф прямых и транзитивных зависимостей NuGet-пакета
алгоритмом DFS без рекурсии. Поддерживаются фильтр по подстроке, циклы
и локальный тестовый репозиторий. Используется стандартная библиотека Python;
менеджеры пакетов и сторонние библиотеки получения зависимостей не нужны.
Этап 4 добавляет порядок загрузки через `--load-order` к обновлённой
ветке `stage3`; изменения её тестов и документации сохранены.

## Запуск

Нужен Python 3.10+. Команды выполняются из корня проекта.
Для NuGet нужен доступ к HTTP(S) репозиторию; тестовый режим работает без сети.

```sh
python3 src/main.py --package jQuery.Validation --version 1.21.0 \
  --repository https://api.nuget.org/v3/index.json --output graph.svg
```

```text
jQuery.Validation@1.21.0: jQuery@1.4.4
jQuery@1.4.4:
```

Вывод — список смежности: `пакет: зависимости`, для NuGet — `имя@версия`.
Листовая вершина выводится с пустым списком. Строки идут в порядке открытия
вершин DFS, рёбра — в порядке описания. Вывод начинается после построения
всего графа. С флагом `--load-order` выводится порядок загрузки.
PlantUML и создание SVG относятся к этапу 5 и здесь не реализованы.

## Параметры

| Опция | Назначение |
| --- | --- |
| `--package` | Обязательное имя исходного пакета. |
| `--repository` | Обязательный URL индекса NuGet V3 или путь к тестовому файлу. |
| `--version` | Обязательная версия: 1–4 числовых компонента, возможны суффиксы. |
| `--output` | Обязательный путь `.svg` в доступном для записи каталоге; файл не изменяется. |
| `--filter` | Подстрока в именах исключаемых пакетов, по умолчанию пустая. |
| `--test-mode` | Читать локальный тестовый файл вместо NuGet. |
| `--load-order` | Вывести порядок загрузки вместо списка смежности. |

Сохранена проверка параметров этапа 1: запрещены управляющие символы,
неверные URL, неизвестные и сокращённые опции, фильтр только из пробелов.
Проверяются читаемость тестового файла и путь SVG без создания файла.
Относительные пути отсчитываются от текущего каталога; поддерживается `~`.
Флаги `--test-mode` и `--load-order` не принимают значений.
Справка: `python3 src/main.py --help`.

## Построение графа

DFS использует явный стек пар «вершина, итератор зависимостей».
Новая вершина отмечается посещённой и помещается в стек сразу при обнаружении;
после исчерпания зависимостей её итератор удаляется. Рекурсия не используется.
Циклы и самопетли сохраняются как рёбра, повторный обход вершины не выполняется.
Рёбра к общим зависимостям сохраняются, одинаковые рёбра объединяются.
Несвязанные с исходным пакетом компоненты не обходятся.

Фильтр — обычная подстрока **с учётом регистра**, без шаблонов.
Пустой фильтр ничего не исключает. Проверка выполняется до выбора версии
и запроса исключаемого пакета. Его ветвь не обходится; потомок остаётся
в графе, если достижим другим путём. Исключение исходного пакета даёт
пустой граф и в режиме NuGet не вызывает сетевых запросов.

Для NuGet адрес `PackageBaseAddress/3.0.0` находится в индексе репозитория.
Загружается `.nuspec` точно указанной версии исходного пакета. Для каждой
разрешённой зависимости запрашивается список доступных версий и выбирается
минимальная подходящая версия по ограничению `.nuspec`.
Поддержаны минимум `1.0`, точная версия `[1.0]`, интервалы `[1.0,2.0)`
и открытые границы `[1.0,)`, `(,2.0]`. Без ограничения выбирается минимальная
стабильная версия; prerelease допускается, если он указан в границе диапазона.
Числовые части версии и prerelease сравниваются как числа.

Версии нормализуются: удаляются начальные нули, метаданные после `+`
и четвёртый нулевой компонент, недостающие компоненты дополняются до трёх,
prerelease переводится в нижний регистр. Например, `01.2.003.0+build` → `1.2.3`.
Вершина определяется именем без учёта регистра и конкретной версией;
для вывода сохраняется первое написание имени. Разные версии — разные вершины.
Все группы платформ объединяются; ограничения разрешаются для каждого ребра
отдельно, без глобального согласования версий для установки.

Индекс сервиса и список версий каждого имени кешируются. Каждый манифест
читается один раз на вершину. Одинаковые ограничения разрешаются один раз.
XML поддерживает пространство имён на `package` или только на `metadata`.

## Тестовый репозиторий и примеры

Файл UTF-8, в том числе с BOM, содержит строки вида:

```text
A: B C
B: C
C:
```

Имена состоят из букв `A-Z`. Каждый пакет, включая листовой, описывается
ровно один раз; порядок объявлений произвольный. Пустые строки и пробелы
вокруг `:` разрешены, повторяющиеся рёбра объединяются. Комментарии, версии,
цифры и строчные буквы не поддерживаются. Проверяется весь файл, включая
недостижимые компоненты. Пустой файл и отсутствие исходного пакета — ошибки.
`--version` проверяется, но в тестовом формате не используется.

```sh
make run ARGS="--package A --version 1.0.0 --test-mode \
--repository examples/diamond.txt --output graph.svg"
```

```text
A: B C
B: D
D:
C: D
```

Общий потомок `D` посещается один раз, ребро `C → D` сохраняется.
Несвязная компонента `X → Y` не выводится.

```sh
python3 src/main.py --package A --version 1.0.0 --test-mode --filter B \
  --repository examples/diamond.txt --output graph.svg
```

```text
A: C
C: D
D:
```

`B` исключён; `D` достижим через `C`. Фильтр `A` даёт сообщение
`Граф пуст: исходный пакет исключён фильтром.`
Другие случаи запускаются той же командой без `--filter`, с заменой файла:

| Файл | Результат |
| --- | --- |
| `examples/repository.txt` | Транзитивность: `A: B C`, `B: C`, `C:`. |
| `examples/cycle.txt` | Цикл: `A: B`, `B: C`, `C: A`. |
| `examples/self_loop.txt` | Самопетля: `A: A`. |

С `--package C --repository examples/repository.txt` выводится лист `C:`.

## Порядок загрузки зависимостей: этап 4

Режим включается флагом `--load-order`. Без него по-прежнему выводится
список смежности. Все остальные параметры, включая обязательный `--output`,
сохраняются. Изображение не создаётся и существующий SVG не изменяется.

Порядок загрузки понимается как последовательность подготовки пакетов,
в которой все зависимости пакета уже подготовлены к моменту самого пакета.
Это топологический порядок с зависимостями перед потребителем. Каждая
вершина выводится один раз, по одной на строку; исходный пакет включён
и стоит последним. Для NuGet сохраняется формат `имя@версия`.

После построения графа применяется DFS без рекурсии с явным стеком:

1. Поместить вершину и итератор её зависимостей в стек активного пути.
2. Перейти к ещё не завершённой зависимости в порядке объявления рёбер.
3. Когда все зависимости вершины завершены, добавить её в результат.
4. Ребро к вершине активного пути означает цикл: вернуть ошибку с его путём.

Для независимых ветвей допустимо несколько порядков. Выбран воспроизводимый
порядок завершения DFS по порядку рёбер исходного графа. Общая зависимость
выводится до всех её потребителей. Операция занимает `O(V + E)` времени
и `O(V)` дополнительной памяти, где `V` и `E` — вершины и рёбра построенного
графа. Сам граф строится неизменённым алгоритмом этапа 3.

Фильтрация выполняется до вычисления порядка: исключённые пакеты и ветви
не участвуют. Недостижимые компоненты, включая циклические, не участвуют.
Цикл или самопетля в достижимом графе делают порядок невозможным.
В этом случае код завершения `2`, сообщение отправляется в `stderr`,
`stdout` остаётся пустым, даже если часть ветвей уже обработана.
Весь результат вычисляется до начала вывода.

### Транзитивные зависимости

```sh
python3 src/main.py --package A --version 1.0.0 \
  --repository examples/repository.txt --test-mode \
  --output graph.svg --load-order
```

```text
C
B
A
```

В файле `A` зависит от `B` и `C`, а `B` — от `C`. Поэтому `C` идёт первым,
затем `B`, затем `A`.

### Общий потомок, фильтр и несвязная компонента

```sh
python3 src/main.py --package A --version 1.0.0 \
  --repository examples/diamond.txt --test-mode \
  --output graph.svg --load-order
```

```text
D
B
C
A
```

`D` нужен обоим пакетам `B` и `C`, но выводится один раз. Компонента `X → Y`
не входит в результат. При добавлении `--filter B` результат — `D`, `C`, `A`,
каждый на отдельной строке. При `--filter A`:

```text
Порядок загрузки пуст: исходный пакет исключён фильтром.
```

### Листовой пакет, цикл и самопетля

```sh
python3 src/main.py --package C --version 1.0.0 \
  --repository examples/repository.txt --test-mode \
  --output graph.svg --load-order
```

Результат — одна строка `C`. Примеры циклов:

```sh
python3 src/main.py --package A --version 1.0.0 \
  --repository examples/cycle.txt --test-mode \
  --output graph.svg --load-order
python3 src/main.py --package A --version 1.0.0 \
  --repository examples/self_loop.txt --test-mode \
  --output graph.svg --load-order
```

Первый запуск возвращает ошибку:

```text
Ошибка: порядок загрузки невозможен: цикл A -> B -> C -> A
```

Второй возвращает `Ошибка: порядок загрузки невозможен: цикл A -> A`.
Оба завершаются с кодом `2`, без частичного порядка в `stdout`.

## Сравнение с реальным NuGet

Сравнение фактически выполнено 20.10.2026: .NET SDK **8.0.426**,
NuGet **6.11.2.1**, проект `PackageReference` для `net8.0`, источник
`https://api.nuget.org/v3/index.json`, точная версия `jQuery.Validation 1.21.0`.
Кеши SDK и NuGet изолированы во временном каталоге, кеш пакетов изначально
пустой. Менеджер пакетов используется только для проверки результатов,
приложение его не вызывает.

Повторная проверка **27.10.2026** выполнена с теми же версиями SDK и NuGet
в новом временном каталоге. Для каждого примера использован отдельный пустой
кеш пакетов и HTTP. Оба `dotnet restore` завершились с кодом `0`.

| Исходный пакет | Вывод `--load-order` | GET архивов в журнале NuGet |
| --- | --- | --- |
| `jQuery.Validation 1.21.0` | `jQuery 1.4.4` → `jQuery.Validation 1.21.0` | `jQuery.Validation` → `jQuery` |
| `jQuery 1.4.4` | Только `jQuery 1.4.4` | Только `jQuery 1.4.4` |

Для обоих запусков состав пакетов и версии из нашего вывода проверены
по `targets` файла `obj/project.assets.json` реального NuGet. Дополнительно
проверено, что каждая зависимость из этого файла предшествует своему
потребителю в нашем порядке. В первом примере NuGet подтвердил зависимость
`jQuery.Validation 1.21.0` от `jQuery 1.4.4`. Во втором зависимостей нет,
поэтому различий состава и последовательности не обнаружено.

Чтобы повторить второй пример, в копии `Compare.csproj` заменить
`Include="jQuery.Validation" Version="[1.21.0]"` на
`Include="jQuery" Version="[1.4.4]"`, выполнить restore в новом временном
каталоге и запустить нашу программу с `--package jQuery --version 1.4.4`.

Команда нашей программы:

```sh
python3 src/main.py --package jQuery.Validation --version 1.21.0 \
  --repository https://api.nuget.org/v3/index.json \
  --output graph.svg --load-order
```

Полученный результат:

```text
jQuery@1.4.4
jQuery.Validation@1.21.0
```

Для повторения сравнения нужен установленный .NET SDK 8. Из корня репозитория
скопировать подготовленные исходные настройки во временный каталог:

```sh
comparison_dir=$(mktemp -d)
cp examples/nuget/Compare.csproj examples/nuget/NuGet.Config "$comparison_dir/"
export DOTNET_CLI_HOME="$comparison_dir/cli"
export NUGET_PACKAGES="$comparison_dir/packages"
export NUGET_HTTP_CACHE_PATH="$comparison_dir/cache"
export DOTNET_CLI_TELEMETRY_OPTOUT=1
export DOTNET_SKIP_FIRST_TIME_EXPERIENCE=1
export DOTNET_GENERATE_ASPNET_CERTIFICATE=false
dotnet --version
dotnet nuget --version
dotnet restore "$comparison_dir/Compare.csproj" \
  --configfile "$comparison_dir/NuGet.Config" \
  --no-cache --force --verbosity normal > "$comparison_dir/restore.log" 2>&1
cat "$comparison_dir/restore.log"
```

В `Compare.csproj` указано точное ограничение `[1.21.0]`; аудит уязвимостей
отключён только для этого сравнения, чтобы журнал содержал запросы пакетов.
`NuGet.Config` оставляет единственный источник nuget.org. Сам SDK был временно
распакован в `/tmp` официальным `dotnet-install.sh --channel 8.0 --no-path`;
системная установка не менялась. Пакеты и артефакты NuGet в Git не добавляются.

Наблюдавшиеся результаты:

| Что сравнивается | Наша программа | Реальный NuGet |
| --- | --- | --- |
| Пакеты и версии | `jQuery 1.4.4`, `jQuery.Validation 1.21.0` | Те же две версии. |
| Ребро зависимости | `jQuery.Validation → jQuery` | То же ребро в `project.assets.json`. |
| Вывод / GET архивов | `jQuery` → `jQuery.Validation` | `jQuery.Validation` → `jQuery`. |
| Итог восстановления | Готовый порядок, код `0` | Два пакета, код `0`, без ошибок и предупреждений. |

Журнал реального запуска содержал запросы архивов в следующем порядке
(между ними также выполнялись запросы `index.json`):

```text
GET https://api.nuget.org/v3-flatcontainer/jquery.validation/1.21.0/jquery.validation.1.21.0.nupkg
GET https://api.nuget.org/v3-flatcontainer/jquery/1.4.4/jquery.1.4.4.nupkg
```

В `obj/project.assets.json` получены вершины `jQuery/1.4.4`
и `jQuery.Validation/1.21.0`; вторая содержит зависимость `jQuery: 1.4.4`.
Это подтверждает совпадение состава, версий и направления зависимости.
Порядок ключей JSON не считается порядком загрузки.

Расхождение в последовательности объясняется назначением операций:
программа строит порядок готовности зависимостей, NuGet выполняет restore —
скачивание и распаковку архивов. В этом запуске NuGet сначала получил архив
исходного пакета, затем архив его зависимости. Скачивание архива возможно
до получения его зависимостей; это не нарушает зависимость в итоговом графе.
Поэтому порядок HTTP-запросов или строк «Установлено» не обязан совпадать
с топологическим порядком. При других запусках на него также могут влиять
кеш и параллельная работа; в программе порядок определяется графом.

Для других пакетов возможны и различия состава: программа этапа 3 объединяет
группы платформ и разрешает каждое ребро отдельно, а NuGet выбирает зависимости
для целевой платформы и согласует одну версию пакета на проект. Пользовательский
фильтр также намеренно исключает часть графа. На выбранном примере без фильтра
эти различия не проявились. Изменять разрешение зависимостей этапа 3 для этого
сравнения не потребовалось.

Официальные описания Microsoft:
[Package Restore](https://learn.microsoft.com/en-us/nuget/consume-packages/package-restore),
[разрешение зависимостей](https://learn.microsoft.com/en-us/nuget/concepts/dependency-resolution).

## Ошибки и тесты

Успешный запуск и `--help` возвращают `0`, ошибка — `2` с сообщением
в `stderr`, без частичного графа в `stdout`. Обрабатываются ошибки параметров,
чтения и кодировки файла, формата графа, HTTP, соединения, JSON и XML,
отсутствие пакета/версии, некорректные диапазоны и списки версий.
При `--load-order` достижимый цикл также даёт ошибку с путём цикла;
частичный порядок в `stdout` не выводится.
Тайм-аут сетевой операции — 20 секунд. Проверка TLS включена;
при ошибках сертификатов настройте хранилище Python или `SSL_CERT_FILE`.

```sh
make build  # Проверка компиляции
make test   # Все тесты
```

Без `make`:

```sh
python3 -m compileall -q src
python3 -m unittest discover -s tests -v
```

Тесты проверяют параметры, NuGet, диапазоны, циклы, фильтрацию,
общие зависимости, разные версии, кеширование, ошибки и сохранность SVG.
Цепочка из 1500 вершин проверяет отсутствие рекурсии.
Используется локальный WSGI HTTP-сервер из стандартной библиотеки;
внешняя сеть не нужна, окружение должно разрешать локальные сокеты.
Для каждого CLI-теста создаются отдельные сервер и временный каталог;
ресурсы освобождаются при успехе, падении теста и ошибке подготовки.
Всего 71 тест, включая 15 тестов этапа 4: порядок на различных графах,
фильтры, циклы, разные версии и CLI с файловым и HTTP-репозиторием.
Служебные файлы и результаты сборки исключены через `.gitignore`.
